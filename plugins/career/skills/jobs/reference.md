# Jobs reference

The career plugin ships the fixed job-search engine and the /jobs skill. The person owns the search: resume, facts, preferences, targets, clients and learned site structure live in their workspace. Start with one working search and adapt it when asked.

Contents: [workspace and setup](#workspace-and-setup), [site classification](#site-classification), [screening](#screening), [writing](#writing), [reuse](#reuse-and-external-code), [checks and deployment](#checks-and-deployment), [workflow](#one-local-entrance), [browser and messaging](#browser-and-messaging-entrances).

## Workspace and setup

Default home is `~/.devdroid/career`; `CAREER_HOME` selects another owned directory outside the installed plugin. No personal record belongs in the plugin, including in fixtures, recipes, defaults or a generated app project. Never borrow an account, bridge, device, host, destination, target list or personal answer from a working installation.

`tools/setup.py --workspace PATH --marketplace CATALOG` installs declared dependencies through the stock plugin installer, then prepares sources and inactive services. Invalid explicit dependency overrides refuse. The required entrances are /sign-in, /ask and /apple-docs. /text is optional and never installed as a career requirement; no dependency code is vendored. The declared `dependencies.json` install command must be invoked by an onboarding picker; native installation has no automatic dependency hook here. Use the registered catalog containing those plugins.

Preparation copies engine tools/scripts and the skill, then materializes the website and app examples as workspace `web/` and `app/`. The plugin holds each client once, under `skills/jobs/examples/`. Existing workspace sources, settings and service templates are retained. This is a starter copy, not an upgrade command that overwrites a person's customizations.

Set `CAREER_HOME` and run the workspace's `scripts/setup.sh`. It creates a venv and installs requirements and locked npm packages; it starts no service. Mac and Linux run the server and website. The Apple build host needs a Mac with Xcode and signing; the checker reports those missing on a Linux-only installation rather than pretending the phone is deployable.

Read the supplied resume, retaining the original. Propose the profile and target roles/companies in chat. Save what the person rules once, with `career.py save --target JSON --value-file FILE`. The example setup is a complete command sequence. No feature questionnaire is generated. A coordinator may save a chat answer without a phone/web provenance receipt; the caller must distinguish a real ruling from its own draft. Ordinary profile/preferences are not application submit approval.

The proposal worker `career.py setup resume.txt` returns `{profile, targets}`, caches the proposal and retains existing profile/targets and the configured resume. It creates no Questions. A later correction does not require rerunning the proposal. `save` uses the same validated effects as Questions:
- `{"setup_object":"profile"}` or `{"setup_object":"targets"}` saves an agreed JSON object. Existing data is protected; deliberate replacement needs `replace:true`. An optional `base_digest` protects concurrent edits.
- `{"setting":"resume_pdf"}` and other recognized settings store scalar choices. Coordinator takes JSON with `agent` and `session`, optionally `host`; word threshold is a positive integer.
- `{"profile_key":"contact.email"}` updates a fact. Labels under `standard_answers.` are literal, including dots and punctuation.
- Form/country/site targets include `posting_id`. Authorization answers also include the confirmed country. Scope mismatches refuse.
- Questions remains a queue/thread and answer editor in both clients. It is never a setup prerequisite or the only valid source of an answer.

Defaults enable company scans, recipes and assistance; WhatsApp stays off until the person chooses it, writes stay disabled until requested. Record only choices that matter now: resume material, target companies, the /sign-in account/site and coordinator; configure Apple signing and device as part of client setup. Additional preferences are saved as they arise. A saved `Ask me every time` answer is a reuse policy, not a repeatedly unanswered setup question. Never assume a PDF choice, visa, age, demographics, location preference, salary or project ranking.

## Site classification

Classify the employer's destination once, record its `ats` and feed metadata in `companies.yml`, then classify any apply handoff again. Discovery and application are separate operations. An endpoint in this table is a structural pattern, not evidence that an employer currently supports it. Inspect the actual public company page before configuring it. Supported scanner parsers are executable in `tools/scan.mjs`; other rows are instructions for a person's requested adapter, not promised features.

| Site type | Detection and public discovery | Application knowledge |
|---|---|---|
| Public job-board feed | One of the `ats` formats `tools/scan.mjs` parses, with the board or tenant recorded in `companies.yml` | Application forms vary per employer. Read every box back by its label; hidden radios and styled upload controls need visibility and label checks. Resume parsing can silently alter dates, education and history. Multi-step wizards may split personal information, experience, questions, disclosures and review. Visible CAPTCHA challenges and automated-browser rejections belong to the person; never bypass them or claim success without evidence. Do not reuse one employer's account proof for another. |
| Custom JSON | Explicit `feed: {url, items, title, link, location}` with dot paths | Use the page's own public endpoint. Resolve apply links to their real system; discovery is not login or permission to submit. |
| Other employer site | The company's own career page, a hosted careers widget or custom HTML | Inspect the public page or endpoint. Discovery does not prove the application form's shape, and the page may hand off to another system, so classify that target too. Build an adapter only when asked, with no silent fallback; do not import a large per-site actuator, and extend the generic reader only when its invariants can be verified. Accounts and consent remain personal actions. |
| Email/referral/direct form | A person supplies the lead | Prepare material and a draft only. The core has no email-sending connector; application approval and personal actions still apply. |

Company scans use public HTTPS only; a feed's search request is a read query even when sent as POST. Manual leads from a community or referral resolve to the company's own site. `examples/platforms.yml` illustrates this distinction; it is agent input, not a second scanner config. Career names no websites: a site the person wants searched or applied on is built with their agent when they ask, on the context /sign-in verifies.

The scanner writes one record per posting URL, pipeline rows and scan history. It preserves explicit country metadata and known variants. Multiple countries or an unknown location do not become the person's home country. Configure target/title/location filters from that person's preferences. A missing/failed feed is a failure to repair, not proof that no roles exist.

## Screening

The example screening program is a complete proposal tool, not an actuator. Run it on a person's profile and rules after copying it to their workspace. Specific structural matches precede generic ones; source fact labels and context are explicit. Unknown/unconfirmed values and Ask me every time return no value.

Never port a default Yes/No for age, enrollment, sponsorship, nationality, prior employment, noncompetes, relationships or location. An absence from a resume is not a negative answer. A university role can affect government-employment wording; contractor and employer wording can differ. A future need is different from current authorization. Broad keyword matches must never choose the polarity for a real form; verify the exact live question and allowed options. Match exact options or declared same-meaning alternatives, never substring guesses (US is not Australia; Male is not Female). Missing context is collected in the job's thread or chat.

Passwords, codes, consent, terms, arbitration, certification, signature, checkbox acknowledgements and account creation are actions for the person. A screening rule cannot authorize them. The fixed policy is stricter than any external filler that automatically checks consent. Keep those rules out of answer maps entirely.

## Writing

Copy `examples/writing.md` to the workspace and adapt from the person's preferences. Its rules concern evidence, agency, relevance, accuracy, length limits and reuse. The drafter and reviewer receive it when it exists at workspace `WRITING.md`. Use earlier approved answers as evidence and framing; do not transplant assertions about an employer or role.

Before drafting, read the verbatim question, unit and limit, the actual posting, and relevant supplied work. Pick the strongest relevant evidence, state the person's actual role/result and relate it to the employer's stated problem. Each essay should do a different job. Verify claims, artifact names, dates and publication status against source material. Supplied work beyond the resume can count when its provenance and status are clear. Unknown private facts remain questions, not confident guesses.

The interview backtrack test is useful: could this person defend every sentence? Keep supported claims, soften overstated verbs and drop inventions. Check agency (built versus managed), team versus individual credit, prototype versus shipped, simulated versus physical, and submitted versus published. An edited/approved answer is not repeatedly rewritten unless the person reopens it or material facts change.

Do not impose a particular applicant's voice notes, punctuation bans, resume length, model choice, word count, favored project, employer ranking, metrics, biography or authorization answers. Personal taste belongs in the workspace.

## Reuse and external code

Keep one spine: JSON posting records, the workflow, local API and both clients. Do not adopt another project's tracker identity, CV builder, fit score or plugin system just to reuse a small helper. The retained scanner, posting guard and icon notices remain in `THIRD_PARTY_NOTICES.md` with their licenses.

When a request warrants extending the system, inspect all local copies before choosing the implementation. Useful independent pieces include posting prompt-injection detection, exact option matching, public-feed liveness, source-fact checks before rendering, PDF text-layer checks after rendering, stable company/variant normalization, and explicit accepted-rule ledgers. These are evaluation targets, not a list of shipped features. A build is not ATS-readable merely because the PDF renders; inspect the text layer and date ranges. A posting is not safe merely because it is JSON; run the posting guard before drafting.

Never copy unlicensed code or imports that depend on a private installation. Retained third-party code keeps its full notice; concepts can be reimplemented. Reject external defaults that conflict with approved agent submission, /sign-in context ownership, person-performed legal actions. Do not port mail watchers, model mandates, portfolio machinery or competition engines into the core. A competition request is an occasion for a person's agent to build a workspace extension, not a setup feature.

## Checks and deployment

`career.py check` (also `career.py doctor` or `tools/doctor.py`) reports capabilities and returns nonzero for broken or unverified requirements. It does not install, fill, submit, build, deploy or send messages. It checks workspace/profile/resume, Python/Node, required dependency entrances and coordinator, each selected role’s CLI/model, the optional WhatsApp group only when enabled, the exact pinned OpenCLI version, a live /sign-in account/site/context proof, a scanner dry run, and Apple build/signing/device/publication configuration. There is no Questions receipt or answer-source test.

`--offline` contacts neither sign-in nor public feeds. Their checks explicitly remain unverified and the overall result is not ready. An offline report is not evidence of live readiness. A configured device ID is not evidence of current reachability. A published IPA and signing identity are local deployment prerequisites; only an actual authorized install verifies the phone path end to end. A doctor is a diagnosis, never a feature interview.

Deploy-when-away is core:
1. On the Mac, configure Xcode with the person's Apple account/team. The person registers/pairs the phone and enables Developer Mode. Save `apple_team_id`, `bundle_id_prefix` and `phone_device` in workspace settings, not in sources.
2. Save `ota_base` as a reachable HTTPS origin. The server serves `/app/install/TOKEN/`, manifest.plist and Career.ipa. The install token is independent of the API bearer token; it opens only these three resources. Tokens are stored in `.private/`, redacted from server logs, and never embedded in the plugin. Invalid tokens return 404 and count toward rate limiting.
3. Run workspace `app/ota.sh` when a build is authorized. `tools/build_app.py` generates the project with workspace signing values, reserves a monotonically increasing build number, archives, exports a debugging-signed IPA and publishes metadata/bytes. A failed build never overwrites the published app. Build and deploy publication share a lock.
4. Activate the staged `.private/services/dev.career.phone-deploy.plist` when the person asks for the service. It wakes every 180 seconds. The watcher reads CoreDevice's device table, then lock state and installed bundle build. Missing/locked/unreachable phones are normal idle states. Unknown device-query results never authorize installation.
5. A newer published build installs only on the configured, reachable, unlocked phone. The IPA is unpacked with ditto to preserve signing attributes; devicectl consumes the app bundle using its supported JSON-output interface. Install errors back off for 30 minutes for that build. A newer build can proceed. Successful installation replaces a running app and may close it.
6. When enabled, the watcher notifies only the dedicated career group through /text and retains failed notification state in `data/ota/notification.json`. It does not reinstall to retry a notification. State, publication and build counters are workspace-only.
7. A Safari install page is available for manual OTA install where supported; it is not an invisible self-update mechanism. Automatic away deployment requires the Mac to reach the paired phone (usually the same reachable network); an unlocked phone on an unrelated network cannot be promised automatic delivery. No cable/TestFlight deployment was verified by this refactor.

Apple's current [registered-device distribution guide](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices) documents pairing, registration, Debugging export and Developer Mode. Fetch /apple-docs when changing app code or distribution. Do not assume a free account, expired profile or unregistered device supports away deployment. Fix actual signing/configuration failures from the checker.

The server binds loopback by default. `serve.py --bind 127.0.0.1 --link-bind off` runs local-only; pairing is generated privately. Remote API access is a separate deliberate network change. Private mesh requires the person's network; Public HTTPS requires a saved choice and `scripts/funnel.sh on` with the selected ports. Publishing an IPA origin does not itself publish the API. Pairing tokens, install tokens and host details remain private.

## Drafting and review choices

Ask once, separately, for `drafter` and `reviewer`, each `{agent, model}`. The person may mix Claude and Codex regardless of the coordinator. Recommend Claude Opus for drafting and Claude Sonnet for review; these are recommendations, not defaults. `career.py models` reports installed choices: aliases listed by Claude’s help, and Codex’s [model/list protocol](https://learn.chatgpt.com/docs/app-server), without an agent turn. Save each JSON choice through `career.py save --target '{"setting":"drafter"}' --value-file choice.json` or the reviewer target. Settings in both clients use the same entrance. Existing `agent` values migrate to both role providers; an unknown old model remains unset until ruled on. Checks never write migration state. Setup or a saved change persists migration in the chosen workspace.

WhatsApp is one optional saved yes/no choice, not a setup dependency. New settings leave it unanswered and silent. Failed or uncertain group creation is recorded before retrying; an uncertain creation is never replayed automatically. Career records notices locally, also shown in app chat, when WhatsApp is off. Replies and application comments still reach the coordinator through /ask. No feature depends on a WhatsApp receipt.

## Client views and freshness

The website and iPhone app use the same authenticated API and workflow. A round speech-bubble button opens chat above the current screen, with an unread badge and Attach job; there is no separate chat page or tab. The web panel lifts above detail/composer bars and fills screens below 560 px. Native screens use the same floating launcher and chat sheet. Today is first and shows the coordinator’s curated review batch, with cleared rows under a toggle. Today and Listings begin with Ready to submit (including an Approve submit row button), Needs your answer and On hold. Row approval opens the current read-back and confirmation, bound to that displayed digest. Listings holds discovery; Questions shows open questions and application replies, then Ready to submit, then On hold. A current submit approval moves an application into Applied immediately. A new comment or edit revokes approval and returns it to On hold. Submitted, interview, offer, rejected and closed records retain their timeline in Applied.

| Route | Contract |
|---|---|
| `GET /stamp` | Opaque data and website revisions. Includes posting, question, application, batch, chat, answer, profile, settings and published-build changes. It returns optional `build` and `install` fields for a published IPA with a configured HTTPS origin and existing scoped install capability; never includes the API token. |
| `GET /chat?since=N` | Ordered chat messages newer than N; the floating chat polls without navigating away, marks agent replies seen locally, preserves drafts and can attach a job reference. |
| `GET/POST /notifications` | Saved opt-in, dedicated group, local notices and failures. POST accepts only an explicit boolean `enabled`; it never accepts a DM destination. |
| `GET /models`, `GET/POST /settings` | Installed model catalog and independent role choices; POST validates the selected model through the same chat-save effect. |
| `POST /postings/ID/confirm` | Resolve an existing uncertain attempt only after the workflow observes positive confirmation in its verified tab; saves evidence and never presses Submit. |
| `GET /batch` | `{created_at, note, items: [{why, record}], open, cleared, missing}`. Current records are resolved on every read: `new` and `enriched` are open, all other states are cleared. Open items come first, retaining batch order within each group. Missing or malformed postings are reported by id. |
| `GET /postings/ID/preview` | All read-back fields, proposed edits separately, destinations, submission terms, open comments and the current gate/action. File values contain their filename. |
| `POST /postings/ID/review` | Existing box entrance: Edit / Use my text preserves the person's exact value and holds submission until the working agent reads it back. Optional deliberate blanks persist across refills. Required facts supplied here also resolve their individual Questions items. |
| `GET /postings/ID/review` | Versioned review boxes with stable keys, current `value_changed_at` tokens and summary counts; the same stored workflow review. |
| `POST /postings/ID/review/KEY/approve` | Approve the exact box version shown (`seen`); stale tokens refuse. |
| `POST /postings/ID/review/KEY/edit` | Save `text` through the normal personal edit entrance; removes submit approval until readback. |
| `POST /postings/ID/review/KEY/comment` | Save `text` as an application field comment; submission stays held until resolved. |
| `GET /chat/page?since=N` | Phone chat cursor response: `{messages, last}`; the existing `/chat` list remains available. |
| `POST /postings/ID/applied` | Observes positive confirmation through the existing confirm entrance; cannot mark a posting submitted by assertion. |
| `POST /chat` | Optional `posting_id` and `field_name` attach an application or field comment. Every unresolved application comment holds submission. The agent resolves it through the existing CLI chat entrance. |
| `POST /postings/ID/approve-submit` | Requires the exact `fill_digest` displayed in the preview. Client refresh must never substitute an unseen digest while the confirmation is open. |

The coordinator writes Today through the CLI, never by editing `data/batch.json`. `batch set` replaces the selection; `add` appends new ids and updates supplied reasons without reordering existing items; `show` returns the same resolved JSON as HTTP; `clear` empties it. Unknown ids, duplicate ids and missing reasons refuse before writing. Selection grants no application approval.

```sh
# reasons.json: {"example-role": "A relevant role with a stated deadline."}
python tools/career.py batch set --why-file reasons.json --note "Review these first."
python tools/career.py batch add --why-file more-reasons.tsv
python tools/career.py batch show
python tools/career.py batch clear
```

`career.py preview ID` exposes the same preview to the coordinating agent. Client rows open the application without navigating back to Listings. Both clients show a copyable job reference, the company website and stated pay. The scanner extracts compensation prose into `posting.pay` and normalizes recognized USD figures into `pay_normalized`; hourly/yearly conversions assume 40 hours/week and 52 weeks/year. Other currencies retain their stated text without a USD conversion. Missing compensation stays unknown.

Foreground clients poll the revision endpoint every four seconds. They refresh changed data and preserve an open editor or comment draft. The website can reload changed assets once no draft is open; the iPhone shows “Update available (build N)” when the published build is newer than its running binary. Tapping opens the existing OTA installer; dismissing hides that build for this paired server until a newer build is published. Installing that build removes the offer. Foreground polling checks build metadata even when application data has not changed. Failed data refreshes do not advance the saved revision. Enter sends and Shift+Enter inserts a newline; on iPhone the hardware keyboard follows that rule and the on-screen keyboard retains its normal multiline behavior with an explicit Send button.

`career open` keeps its local one-time code exchange at `POST /web/open`. Phone pairing URLs also carry a single-use code, valid for five minutes, redeemed in the body of `POST /pair` (or `/api/pair`). The response carries the API token; generated URLs never carry it. Existing Keychain pairing continues to work. This does not grant automatic access based on a tailnet identity or browser cookies.

## One local entrance

Set CAREER_HOME to the person's workspace. Use its `.venv/bin/python tools/career.py --help`. The CLI and HTTP clients call the same workflow. Agent workers and notifications can be faked without replacing the workflow. Fakes are test fixtures, not a production CLI mode. Production uses stock OpenCLI after /sign-in proves the chosen context. Live writes default to Disabled until the person requests form assistance. For verification, first run `.venv/bin/python -m pip install -r requirements-dev.txt`, then `.venv/bin/python -m pytest tools/test_workflow.py tools/test_recovery.py -q` from the owned workspace to exercise them end to end. Runtime setup deliberately installs only runtime requirements. Tests never use a real employer page.

```
tools/career.py pick POSTING approved
tools/career.py pick POSTING skipped --reason 'not a fit'
tools/career.py fill POSTING
tools/career.py review POSTING
tools/career.py box POSTING 'Exact field name' edit --value-file answer.txt
tools/career.py apply-edits POSTING
tools/career.py gate POSTING
tools/career.py approve-submit POSTING --digest DIGEST_FROM_DISPLAYED_REVIEW
tools/career.py submit POSTING
tools/career.py confirm POSTING
tools/career.py release POSTING
tools/career.py resolve-uncertain POSTING --reason "Inspected and closed the old tab"
tools/career.py tracker
tools/career.py chat --text-file reply.txt --reply --resolve 1
tools/career.py messages
tools/career.py events
tools/career.py recipe POSTING system-name --learning-file learning.json
```

The person approves submission in the app or types yes in an interactive CLI terminal. The approval covers a digest of this application's read-back values. Every edit removes it. Standard fields auto-approve; custom answers at the chosen threshold (25+ words by default) and flagged boxes wait for the person. A block needs an edit. The working agent applies edits and reads back every changed value; there is no second reviewer pass. Stored answers are reused by what makes them true: contact and personal facts apply to the person; authorization applies per country; role-specific answers stay with the canonical application URL. Exact normalized labels and an explicit same-polarity alias list match facts; no substring guesses or fuzzy semantic matching. A missing job country is collected as context in that job's Questions thread before asking for authorization. A correction to the country blocks the stale application approval and its old country answer. Personal answers survive unrelated profile edits and do not depend on submitting the job. Drafted suggestions still invalidate when their supporting material changes. Chat answers and Questions answers use the same store. Only accepted facts are saved. All boxes are visible in the first pass; reuse introduces no extra authorization approval step.

Fill known values across every reachable step, then review them before the person's first pass. A completed review is not rerun on refill. If required missing facts prevent reaching later steps, retain partial coverage and review only newly reachable steps before showing those boxes; never mark an unseen step reviewed. After that review, each missing fact gets its own plain question in Questions, with the field’s exact options and multi-select controls where applicable. Never ask the person for JSON. Reuse the same question on repeated stops; a later successful fill closes stale help questions for that posting, while uncertain submission/navigation outcomes still require the person. Unknown job-country context gets a separate question before country-specific facts. Resume consumes personal answers and saved drafts. A refill does not start a new full review; new or changed form boxes require the person's review. Unconfirmed profile values never reach a drafter. Optional unknown choices stay blank; only exact or explicitly declared alternatives may select an option. Stale question corrections block approval until reapplied. Rebuilding archives prior fill/review and preserves unchanged personal approvals and edits.

One persistent active application spans processes and app requests. Step fields and navigation are checkpointed; Apply enters the form, Next/Back traverse it, and the final approval digest covers every step. Submit revisits and verifies all steps. A later added step gets its own one-time agent review and returns its changed boxes to the person; previously reviewed steps are not reviewed again. A browser restart resumes saved plans. Release before pursuing another form. Before submit, recheck identity, challenge state, URL, all named fields, options, required/type definitions and the submit control against the approved fill. A durable attempted_at precedes the click. If the result is uncertain, inspect that same tab and use confirm to recover positive evidence. Recorded intent is not proof that a click landed or that nothing was sent. Only after personally verifying nothing was sent may the person choose to submit manually and then run confirm; the agent never retries Submit. Empty fields or a vanished form do not prove submission. If confirmation cannot be recovered, the person inspects and closes the tab, then uses resolve-uncertain in the app or CLI. It frees the one-form slot, keeps the record unconfirmed, notifies the person on the failed attempt and never re-enables submit. Only positive confirmation plus a PNG snapshot marks applied. The tracker is rebuilt from local records after every status change and keeps the Notes section.

The API retains the inbox and Questions routes and adds `GET /postings/ID/review`, `POST /postings/ID/review {name,decision,value?,by}`, `GET /chat`, `POST /chat {text,posting_id?,by}`. `GET /postings/ID/approve-submit` returns the gate; POST requires `{fill_digest,by}` from the displayed review and refuses a stale digest. Confirming success belongs to the agent's confirmation entrance. Personal CLI decisions (pick, per-box decisions, submit approval and uncertain release) require the person to type yes in a terminal and are attributed to terminal-person. These are authorization conventions, not a security boundary against an agent with the same local account or bearer token; that agent must not impersonate the person. `POST /postings/ID/resolve-uncertain {reason,by}` records that personal recovery decision. Per-application comments in both clients include posting_id and hold submission until the coordinator resolves them. All API data calls require the workspace bearer token. Static `/web/` and `/app/` contain no private material. `/files/` serves only posting media and application artifacts, never configuration or credentials.

Company scans read the public feeds configured in `companies.yml`: one of the `ats` formats `tools/scan.mjs` parses, or a custom JSON feed (`feed: {url, items, title, link, location}` dot paths). They write inbox records, the pipeline and scan history.

Learned recipes are actual OpenCLI local metadata adapters in `CAREER_HOME/recipes/SYSTEM/index.js`. The recipe entrance saves field names/types from a confirmed application and optional learned `steps` and a generic `confirmation_pattern` from JSON. It emits a package, `opencli-plugin.json` and `learning.json` with the pinned OpenCLI registry peer dependency, validates JavaScript syntax before acceptance, and never stores answers, file paths or permissions. The generated `SYSTEM recipe` command returns that structure. Career reads the saved structural JSON into agent context when a posting has matching `ats` and recipes are enabled; it never executes an adapter during fill. It does not execute a per-system filler. An existing recipe is revised by the person's agent rather than overwritten by the save command. Registration is a separate, reviewed `opencli plugin install file:///absolute/person/recipes/SYSTEM` through the stock plugin entrance; no registration is performed here. This follows the [OpenCLI plugin contract](https://github.com/jackwener/OpenCLI/blob/v2.0.2/docs/guide/plugins.md). A recipe cannot authorize browser writes.

`data/notifications.json`, Questions events and `data/chat.json` retain unsuccessful delivery. /ask enqueue receipts mean queued, never read; Questions events remain pending until the coordinator uses --mark. Failed company scans retain their own schedule lock and bounded command timeout. Failed attempts retry at the next hourly wake; successful scans retain their daily cadence. Inspect uncertain publication before a deliberate retry. Register the current coordinator in private settings and check pending events at session start.

Stop for every password, code, CAPTCHA, consent, terms, signature, certification or account creation. For consent resume, choose the checkbox state in the browser, then confirm completion in chat or Questions (the stored completion is `Confirmed`). Optional boxes may remain unticked. The person performs those steps. Never type sensitive values supplied through Questions, tick any checkbox or treat Create account as Submit. Checkbox actions are conservatively human-only. A read-only Terms link is not consent and is never clicked. Duplicate application URLs and known variants with an attempted submission block before opening, approval or another click.

`GET /answers` lists saved values with their names and truth scopes. `POST /answers/KEY {value,by}` changes a personal answer or saves the literal policy `Ask me every time`. Both Questions clients expose Saved answers. That policy asks once in each new application and retains an answer already given within the application. Country comes from explicit feed metadata, target configuration or a named country in the feed location; unknown or conflicting locations still need context from chat or Questions. Job-specific corrections never become universal country guesses.

## Browser and messaging entrances

A labelled `.file-upload` group is one file field. Its required markers and dormant manual-entry editor are metadata, not extra questions. The reader observes the actual browser File before a component replaces its input with progress and filename views; readback and the atomic submit guard retain its byte hash and verify the displayed filename. A filename alone is insufficient evidence. An unverified or changed attachment can be replaced through that group's own Remove file control and its restored native input. Alternative Attach/cloud/manual-entry buttons are never clicked. The chosen resume comes from settings; an optional cover letter stays empty unless its exact field label has an explicitly supplied local file in profile `standard_answers`. Unknown controls and disabled upload inputs still refuse.

React Select country and education controls on public forms are single named `combobox` answers, with exact option labels. Career opens their rendered lists using stock clicks, observes asynchronous loading and keyboard pagination, then chooses the exact option with a stock click. It never fills their search buffers with answer text. The selected display (including a country's flag identity, not just its shared dial code) is read back. An inspected option catalog is scoped to the application URL and field selector in the workspace's private browser state; writes and submit preflight inspect the live list again. Unknown widgets, ambiguous labels, unfinished searches and lists that do not finish loading refuse explicitly. Hidden validity proxies and the phone library's hidden duplicate search input are ignored only within their recognized widgets. `aria-required` and labelled upload groups determine required status and upload names. Use the exact OpenCLI 2.0.2 executable installed and pinned by /sign-in, resolved by its own `opencli()` entrance (or an absolute `OPENCLI_BIN`). Before every command, `scripts/browser-runtime.mjs` calls the dependency's `compatible({start:false})` guard. A stopped or mismatched daemon refuses; career never starts, restarts or replaces it. Bare PATH lookup is never used. /sign-in handles its own browser installation and account enrollment. No personal adapter dependency or separate career browser setup is required.

The browser object reads named DOM fields through stock `eval`, then uses stock `fill`, `type`, `select`, `check` for radio choices, `upload`, navigation `click`, `screenshot` and `tab close`. The compatibility guard runs before this whole observation. A replay of that expression refuses; there is no native-click fallback for Submit. ## Posting records

One UTF-8 JSON file per posting in the private workspace's `data/postings/ID.json`. Required client fields: `id`, `company`, `title`, `status`. Scanner-created jobs also have `kind: job`, an HTTPS `url`, `source`, `first_seen`, `posting.apply_url`, `ruling` and `history`.

Before filling, the coordinating agent adds `site`, the enrolled employer site name from /sign-in, and any tailored `materials.resume_pdf`. Inbox pick changes `ruling.decision` and status to approved or skipped. A verified fill moves approved to ready. The submit entrance first persists submission_unconfirmed with `submission.attempted_at`; positive confirmation and a PNG snapshot move it to applied. Post-application outcomes remain editable local records and are reflected in the tracker.

`materials.application_dir` and artifact paths start with `applications/`, resolved only under `data/applications/`. Never store credentials in a posting. `form_fill.json` contains named rows and their read-back values. `review.json` contains the same boxes, flags, approval states and a digest of the exact fill. A person's application approval stores that digest under `ruling.submit_digest`. Edits invalidate it.

Optional display fields retained by the clients include location, track, summary_ai (with provenance label), company_info, images, logo, urgency, variants and posting dates. Only job records enter the application workflow.

No records, application artifacts or personal profiles are distributed. Example fixtures under tools/fixtures are synthetic.

## Questions

A private `data/questions/ID.json` thread holds a proposal, the person's answer and any corrections. Common fields: id, asked_at, by, topic, title, question, context, kind (text/choice/yesno/confirm), options, status (open/answered/dismissed), answer, answered_at, answer_source, applies_to, applied, thread, events. Answer source is display metadata, never an acceptance receipt. Chat rulings use the same effects without requiring a Question. An optional command is display-only, with a Copy button in both clients.

Each thread turn has n, role (ask/user), at, by and text. An agent reply reopens the existing thread; it does not create a new question. A note-only reply resolves an open choice as needs_reading. Text questions use the note as their answer. A follow-up can be merged into another thread and is hidden through merged_into.

Effects are applied through tools/questions.py, shared by the CLI and API: profile_key corrects a confirmed profile fact; form_question writes an application answer; ruling:approve picks the job; setup_object:profile or setup_object:targets validates and saves a corrected proposal; setting selects resume_mode, account or review_min_words. An unknown or incomplete value refuses rather than inventing a fact. Setup answers are JSON objects; ordinary field answers are text.

Every app answer/comment is stored as an event before /ask delivery. The installed /ask entrance receives a prompt file; unavailable delivery is saved with its typed error. `questions.py pending --all` lists events still awaiting the coordinator, and --mark acknowledges that the agent read them. There are no direct session sockets or copied /ask code. New-question notifications and pings use the same optional dedicated group as the rest of career, never a personal chat or /text notice group. Tokens are never included in links.

Draft evidence distinguishes person and role. Personal claims quote only résumé/profile excerpts. Motivation and fit reasoning may quote the posting description, `company_info` or `summary_ai` for company/role claims. Mixed answers carry ordered `{text, scope, evidence}` claims that compose the full answer; unsupported drafts leave the actual missing fact for Questions. Role material changes invalidate role-dependent drafts. Saved office selections are reused across applications only for the same listed options; relocation or general onsite permission does not choose offices.

Mixed flat evidence on a motivation draft is repaired once by the drafter into ordered person/role claims before validation. This never relaxes personal evidence requirements. Missing motivation plans written under an older draft contract retry once under the current contract; unchanged current failures do not loop.
