---
name: building-rules
description: The discipline for building and porting software with agents. Use whenever new code is being built, a module is being restructured, code is being ported or consolidated between repos, a bug is being fixed, or a piece of work is about to be called done; also when the user says "building rules", "port this over" or "consolidate".
---

Grow, don't spec. A complex system that works evolved from a simple one that worked. Build the thinnest thread that runs end to end in the real environment, adjust aim from where it lands, and grow everything else on it. A detailed design for code that does not exist yet is fiction with authority. Keep it simple, and build nothing until it is needed (KISS, YAGNI).

Everything goes through one entrance. Whatever a person can do in the app, an agent, a script, the dry run and the test can do through the same entrance to the real code, and none of them gets its own copy. A part of the system an agent cannot reach is a bug, not a gap: fix it before the work counts as done, and when the entrance cannot express something new, grow the entrance. Make the entrance deep: it is everything a caller must know, including invariants, ordering and error modes, and it should give a lot of behaviour for little to learn. A module whose deletion would make its complexity vanish was a pass-through; delete it. A seam is real only when a second adapter exists.

Reuse before you build. When the project keeps an inventory of what exists, read it first, and correct it in the same change when it turns out wrong. Then ask whether it needs to exist, then whether the codebase, a working sibling project, the platform or an existing dependency already does it, and generalise what exists rather than adding a second mechanism beside it, once a second real case needs it. When porting, gather every copy before choosing one, because the fixes live in the copies left behind. Make the smallest complete change: finish every caller and test it reaches, and once tests exist at a deeper interface, delete the old ones beneath it. Small never means cutting validation at trust boundaries, error handling that prevents data loss, or security. Dependencies point one way: the product never depends on the development process, and a fresh clone runs with only the product and its declared inputs.

Fix the cause. The real fix beats the one that unblocks today; when a shortcut is truly unavoidable, one comment says what it limits and when it must be replaced. Fix at the depth of the cause, not with a special case on top, and deepen where the history shows change keeps landing. Toil is refused, not performed: once waste is recognised and its fix is named, stop the line and fix it instead of paying again. A defect in a tool is not a caution to log: fix it now, because leaving it costs more, and log only what cannot be fixed in this session.

Know, don't guess. Before guessing why code exists or patching around a bug, read its history: the session that wrote it and whether the bug was met before (/browse-chat-history), or at least its git history. Decide what is feasible by running or calculating something, never by estimate; measure before you tune and read before you assert. When exploring something for the first time, log everything; once the behaviour is understood, and before calling the work done, cut the logging back and clear your own scratch files. Wait on an event or a checked condition, never a blind delay.

Fail loudly; done means verified. A missing input is a typed refusal, never a silent fallback, and an uncertain answer is never reported as a safe one. Write the command that proves a slice before you build it, and report what it showed: logic-verified is not live-verified, and a skipped step is said out loud. The checker for a kind of artifact passes before the first one is accepted. A check on what already exists reports; a check on what a change does may refuse. Parallel agents each work in their own git worktree and commit before reporting done. A stand-in must behave like the real thing: the real tool's exact output and failures, and real sizes and shapes. A builder's passing run is a claim: someone who did not write the code reruns it in their own environment and reviews it before reading the builder's report. The last check is a fresh agent using the system correctly from its docs alone; if it cannot, the docs failed.

Credit by what survives, not by where you started. Code kept from someone else's published project carries its license and notice however far you have taken it; once none of it remains, a README line saying where the work grew from is courtesy, not obligation. Your own unpublished iterations are never cited: that lineage lives in a gitignored porting ledger, updated in the same change as the port, and every ported name earns its name again at the crossing.

Code states what is true now. No comment, name or doc describes what the code no longer does or only makes sense to someone who knew an earlier version; history belongs to git. Use the design words exactly: module, interface, implementation, depth, seam, adapter, leverage, locality.
