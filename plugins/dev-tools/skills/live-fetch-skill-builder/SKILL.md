---
name: live-fetch-skill-builder
description: Build a skill that teaches agents to fetch a documentation site, API reference, forum or wiki live instead of answering from memory. Use when the user wants a docs skill or live-fetch wrapper for a website, says "make a docs skill for X", "wrap these docs for agents", "agents keep getting X wrong from memory", or wants a vendor's docs, forum or community reachable by agents.
---

Documentation goes stale in a model's memory and in any copy you make of it. A docs skill caches nothing: it teaches the agent the fastest correct way to fetch the current page, and where to start looking.

Build only for what is not already covered. Check for an installed skill on the source, and for a live-docs service the agent already has, such as Context7 for popular libraries. Then confirm with the user before probing: the site, how much of it the skill covers, whether it follows the latest version or pins one, and where the new skill will live.

Measure how the site serves its pages before writing anything, because a skill written for the wrong shape fails silently. Run `scripts/probe.sh <page-url>` on a few representative pages. Prefer, in order: an `llms.txt` index (a ready-made catalog), a markdown version of each page, a JSON feed the page loads (some documentation renderers keep it at a separate path, such as DocC's `/tutorials/data/<path>.json`; the page's scripts or a browser's network panel show it when the probe cannot guess the path), plain HTML, and last, JSON embedded in the HTML, which breaks whenever the site's framework updates. A 403 can mean "not at this path" rather than "forbidden", and a tiny markdown file behind a large page is a stub pointing elsewhere.

The skill is a rule and a map. State the retrieval rule once, with an example URL. Then list entry points grouped by topic, each with what to pull from it: hubs that link deep, not every leaf, so the agent drills in on demand. Look past the docs for the sources that answer real questions: the vendor's forum, GitHub discussions and issues, sample-code repositories, release notes and migration guides, blogs and changelogs, wikis, and recorded sessions or talks. Show the user what you found, each with a recommendation to include, give its own companion skill, or skip, and let them choose. When a vendor has several separate products, give each its own skill under a short router. Write the description in the words people use when they need these docs. Keep the skill itself short: the rule, its exceptions and the map; edge cases an agent can discover from the pages themselves do not belong in it.

Verify with the tool the agent will use. A curl check proves the URL exists; only the agent's own fetch proves the agent can read it, and only a final 200 with the topic's actual content counts, not a title, a redirect choice or a page asking for JavaScript; and some sites block one and not the other, in which case the skill tells the agent to fetch with curl and a browser user agent. Ship at least three tests that need nothing from your machine: the rule returns readable content, the catalog's entries resolve, and a plain question in the domain triggers the skill.
