# Safari Web Extensions — Overview

## What it is

A Safari Web Extension is the **WebExtensions API standard** (the same one Chrome, Firefox, and Edge use) hosted inside a native macOS or iOS app bundle. The extension itself is HTML/CSS/JS; the app bundle is just the delivery vehicle that lets users install through the App Store or run locally.

Two layers, both required:

1. **The WebExtension** (`manifest.json` + JS/HTML/CSS) — identical in shape to a Chrome MV3 extension.
2. **The Xcode host app** — a minimal macOS (or iOS) app whose only purpose is to embed the extension as a system-registered appex. Auto-generated by `safari-web-extension-converter`.

When the host app is run once, macOS's LaunchServices registers the embedded extension; only then does it appear in **Safari → Settings → Extensions**.

## Manifest V3 vs V2

Always use MV3. Safari 16+ supports it; Chrome has already deprecated MV2; Firefox supports both. The MV3 manifest skeleton:

```json
{
  "manifest_version": 3,
  "name": "...",
  "version": "1.0.0",
  "description": "...",
  "permissions": ["activeTab", "scripting"],
  "host_permissions": ["https://target.example.com/*"],
  "background": { "service_worker": "background.js" },
  "action": {
    "default_title": "...",
    "default_popup": "popup.html",
    "default_icon": { "16": "icons/16.png", "48": "icons/48.png", "128": "icons/128.png" }
  },
  "icons": { "16": "icons/16.png", "48": "icons/48.png", "128": "icons/128.png" }
}
```

Key changes from MV2 you'll notice:
- `background.page` / `background.scripts` → `background.service_worker` (single file, transient)
- `browser_action` / `page_action` → unified `action`
- `permissions: ["tabs", "<all_urls>"]` → `permissions` + `host_permissions` separated
- `chrome.runtime.executeScript` → `chrome.scripting.executeScript({ target, func, args })`

## Build flow at a glance

```
extension/ (manifest.json + JS/HTML/CSS + icons/)
        │
        │  xcrun safari-web-extension-converter --copy-resources --swift --macos-only ...
        ▼
HostApp/
├── HostApp.xcodeproj
├── HostApp/                            ← macOS host app target (mostly empty)
└── HostApp Extension/                  ← Safari Web Extension target
    ├── SafariWebExtensionHandler.swift ← Generated bridge; rarely needs edits
    └── Resources/                      ← Copy of extension/ at build time
```

Then:
```bash
xcodebuild -project HostApp.xcodeproj -scheme HostApp \
           -destination 'platform=macOS' -configuration Debug \
           -derivedDataPath ./build build
open ./build/Build/Products/Debug/HostApp.app    # registers the appex with LaunchServices
```

After running the .app once, the extension is discoverable in Safari. In Safari:
1. **Settings → Advanced** → check "Show Develop menu".
2. **Develop → Allow Unsigned Extensions** (resets every launch — see `known-quirks.md`).
3. **Settings → Extensions** → enable the extension.

## Distribution paths

| Path | Signing | Lifecycle | When to use |
|---|---|---|---|
| Dev / unsigned | None | Allow-unsigned toggle resets every Safari launch | Active development on your own Mac |
| Developer-signed | Mac Developer cert | Persists across Safari restarts | Personal/internal use, your own machines |
| App Store | Distribution cert + App Store review | Persists; distributable | Public release |

Notarization is required for distribution outside the App Store. For App-Store-only paths, App Review is the final gate — and Safari extensions go through the same review pipeline as full Mac/iOS apps. Note: extensions cannot be distributed via TestFlight independently of their host app.

## Where to look when stuck

- Service worker console: **Safari → Develop → Web Extension Background Pages → \<your extension\>**
- Popup console: right-click the open popup → Inspect Element
- Content script / injected function console: open the target tab's DevTools (⌘⌥I)
- Build errors: usually the bundle-id case rule — see `known-quirks.md`
- Extension not appearing in Settings: host app hasn't been run yet, or LaunchServices needs `-R` re-registration

## What the converter generates that you usually edit

| File | Edit? | Why |
|---|---|---|
| `manifest.json` | ✅ Always | Permissions, host_permissions, popup wiring |
| `background.js` | ✅ Always | Service worker logic |
| `popup.html` / `popup.js` | ✅ Always | UI surface |
| `content.js` | Sometimes | Only if you declare `content_scripts` |
| `SafariWebExtensionHandler.swift` | Rarely | Bridge between Safari and your extension; default works for 99% of cases |
| `Info.plist` (extension) | Rarely | Bundle id, display name, Safari extension info dict |
| `Info.plist` (host app) | Rarely | App display name |
| `Assets.xcassets` | Sometimes | If you want a non-generic host-app icon |

The `SafariWebExtensionHandler.swift` file is interesting: it's where Safari forwards messages from the extension's JS to native code, if you want to do anything privileged (e.g., write to a directory outside the sandbox, call native frameworks). Most extensions never touch it.

## Cross-browser parity

A well-written MV3 manifest + `const api = browser || chrome;` shim runs unmodified in Safari, Chrome, Firefox, and Edge. The places you'll fork:

- **Downloads**: Safari has no `chrome.downloads` — see `delivery-patterns.md`.
- **Identity / OAuth**: `chrome.identity` works differently on Safari.
- **History / Bookmarks**: not exposed in Safari.
- **Web Request**: limited in Safari; prefer `chrome.declarativeNetRequest`.

For most personal-use extensions (toolbar action → scrape page → emit file), the JS is 100% portable.
